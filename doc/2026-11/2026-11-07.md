## 修改内容

### 1. GoalDirectionCommand 支持外部目标点

文件：`config/command/AllTrackingCommand.py`

`_resample_command()` 现在优先使用外部写入的：

```python
command.target_positions[env_ids]
```

如果不存在，再回退到原来的：

```text
target_distances + 四向单位向量
```

这样其他任务不受影响，梅花桩可以通过 event 直接写入随机目标点。

### 2. 新增梅花桩目标采样 event

文件：`config/event/plum_reset.py`

新增：

```python
def randomize_plum_target(...):
```

采样区域：

```text
梅花桩区域半宽：15 / 2 = 7.5m
外侧平地宽度：2.0m
内侧净距：0.3m
使用带宽：0.7m
```

所以目标点满足：

```text
max(|x|, |y|) ∈ [7.8, 8.5]
```

也就是始终落在绿色外侧平地的靠内区域，不会落到梅花桩上，也不会太靠近平地外缘。

采样方式：

- 随机选择上、下、左、右四条边。
- 沿边随机位置。
- 向平地内侧随机深度。
- 每个 env 独立采样。

### 3. 接入 Plum env_cfg

文件：`task/track/config/env_cfg.py`

在 `my_go2_plum_env_cfg()` 的 reset events 中加入：

```python
"randomize_goal": EventTermCfg(
    func=randomize_plum_target,
    mode="reset",
    params={
        "command_name": "Goal_direction",
        "inner_margin": 0.3,
        "inner_band": 0.7,
    },
),
```

保留原来的 `target_distance=8.5` 作为 fallback；实际每次 reset 都会由 event 覆盖目标点。

### 4. 目标点不再固定方向

以前：

```text
target = (8.5, 0.0)
```

现在：

```text
target = 外侧平地靠内区域的随机点
```

所以机器人可能需要向任意方向转身并穿越梅花桩。

## 10:43 追加记录：桩位改为从平台中心向外交错

### 问题

之前桩位是从 15×15 区域的角落开始铺全局网格，再挖掉中心平台。
这样靠近平台的桩位相位不固定，视觉上会偏向一侧，不符合“从中间平台向外交错分布”。

### 改动

`config/terrain/plum_blossom_field_terrain.py`：

- 网格原点改为**中心平台中心**。
- 行索引从 `-ny_half` 到 `+ny_half` 对称生成。
- 奇数行偏移半个 `pitch`，形成交错。
- 仍然跳过中心平台及其净空区域。
- 外围边界、桩尺寸、桩间距和难度 schedule 不变。

核心逻辑：

```python
nx_half = ceil((field_half_x - half_pillar) / pitch)
ny_half = ceil((field_half_y - half_pillar) / row_pitch)

for iy in range(-ny_half, ny_half + 1):
    row_offset = pitch / 2 if iy % 2 != 0 else 0
    for ix in range(-nx_half, nx_half + 1):
        x = ix * pitch + row_offset
```

### 验证

- 14 行地形正常构建。
- env 构建、reset、step 正常。
- 目标仍在 `max(|x|,|y|) ∈ [7.8, 8.5]`。
- 预览已更新。

### 备注

level 0 的桩是 `2m × 2m`，中心平台是 `3m × 3m`。
由于 `2m` 桩比平台半宽还大，第一圈桩不能无限贴近平台；当前会保留一个平台净空区，这是几何尺寸导致的。
如果希望第一圈桩更贴近平台，需要减小桩尺寸或放宽平台净空/间距。

## 17:07 追加记录：修复 anneal 一上来就到 1e-3

### 原因

`anneal_reward_weight` 原来使用：

```python
env.common_step_counter
```

作为绝对训练进度。

这个 Plum run 是从 Platform 的 checkpoint 恢复的：

```text
load_checkpoint = model_13998.pt
```

`common_step_counter` 也一起恢复，已经远大于：

```text
1000 iter × 24 steps = 24000 steps
```

所以第一次 reset 时 progress 直接是 1.0，权重立刻变成 `1e-3`。

### 修复

1. `TrackOnPolicyRunner.load()` 在加载 checkpoint 后记录本次 run 的起点：

```python
self.env.unwrapped._anneal_start_step = (
    self.env.unwrapped.common_step_counter
)
```

2. `anneal_reward_weight()` 改为按相对步数计算：

```python
start_step = int(getattr(env, "_anneal_start_step", 0))
elapsed_steps = env.common_step_counter - start_step
progress = elapsed_steps / total_steps
```

这样：

```text
新 run：start_step = 0
resume：start_step = 加载 checkpoint 时的 common_step_counter
```

本次 run 的退火会从 1.5 重新开始。

### 验证

用 `common_step_counter = 100000`、`_anneal_start_step = 100000`：

```text
progress 0.0 -> weight 1.500
progress 0.5 -> weight 0.7505
progress 1.0 -> weight 0.001
```

### 注意

- 当前已经在跑的 run 权重已经变成 `1e-3`，需要重启训练才会使用新的相对退火逻辑。
- 重启后从当前 Plum checkpoint resume，会重新从 `1.5` 开始退火。
- DTC 的 `anneal_reward_weight` 如果没有设置 `_anneal_start_step`，仍然按 `0` 起点计算，行为不变。
